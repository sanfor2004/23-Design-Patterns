# Cheat sheet

[Pattern catalog](README.md)

A decision aid for all 23 patterns. “Avoid when” matters just as much as “use when”.

| Pattern catalog | Category | Use when | Avoid when | Memory trick |
| --- | --- | --- | --- | --- |
| [Abstract Factory](creational/abstract-factory/README.md) | Creational Pattern | Use it when several product types must vary together and clients should not choose concrete classes. | Avoid it for one stable product type or when independent choices are actually desirable. | One factory, one matching set. |
| [Builder](creational/builder/README.md) | Creational Pattern | Use it for objects with many independent options or a meaningful validation boundary. | Avoid it for two obvious constructor arguments; a small aggregate with named fields may be clearer. | Choose steps, then build. |
| [Factory Method](creational/factory-method/README.md) | Creational Pattern | Use it when an existing inheritance-based workflow needs an extensible creation step. | Avoid it when passing a ready-made Sender into a function is sufficient; inheritance would add needless structure. | Keep the workflow; override creation. |
| [Prototype](creational/prototype/README.md) | Creational Pattern | Use it when runtime objects carry useful configuration and clients should not reconstruct their concrete types. | Avoid it when ordinary value copying already expresses the requirement clearly. | Copy the setup, not the identity. |
| [Singleton](creational/singleton/README.md) | Creational Pattern | Consider it only when one instance really is a process-level invariant and its lifetime is appropriate. | Avoid it for convenient access to ordinary dependencies. Pass a Metrics reference explicitly when tests need isolation. | One instance can still mean many problems. |
| [Adapter](structural/adapter/README.md) | Structural Pattern | Use it at a boundary to an existing API you cannot or should not change. | Avoid it when you own both sides and a single consistent interface would be simpler. | Translate at the boundary. |
| [Bridge](structural/bridge/README.md) | Structural Pattern | Use it when two axes of variation would otherwise produce a cross-product of subclasses. | Avoid it when only one small dimension changes and a function parameter already handles it. | Two axes, one connection. |
| [Composite](structural/composite/README.md) | Structural Pattern | Use it for genuine part-whole trees where a useful operation applies to both leaves and groups. | Avoid it for a flat list or a graph with shared parents and cycles; tree ownership would misrepresent the domain. | A group answers like one item. |
| [Decorator](structural/decorator/README.md) | Structural Pattern | Use it for optional, composable behavior that preserves the wrapped contract. | Avoid it when a simple list of ingredients and a sum express the entire requirement; this example intentionally illustrates the structure. | Same contract, another layer. |
| [Facade](structural/facade/README.md) | Structural Pattern | Use it when many callers need the same useful subset of a complicated subsystem. | Avoid it for a trivial pass-through that adds no meaningful simplification. | One front door to several services. |
| [Flyweight](structural/flyweight/README.md) | Structural Pattern | Use it after measuring significant duplication of immutable data across many objects. | Avoid it for tiny datasets, mutable per-instance data, or when lookup overhead outweighs savings. | Share the shape; carry the position. |
| [Proxy](structural/proxy/README.md) | Structural Pattern | Use it for lazy initialization, access checks or remote access when a stable subject interface is useful. | Avoid it if direct construction is cheap and the access policy adds no value. | A stand-in guards the real object. |
| [Chain of Responsibility](behavioral/chain-of-responsibility/README.md) | Behavioral Pattern | Use it when request handling order or membership must be composed independently. | Avoid it for two fixed checks in one place; the initial expression is then clearer. | Handle it, or pass it on. |
| [Command](behavioral/command/README.md) | Behavioral Pattern | Use it for deferred actions, queues, macros or undo histories. | Avoid it for a one-off function call with no need to store or schedule intent. | An action you can keep. |
| [Interpreter](behavioral/interpreter/README.md) | Behavioral Pattern | Use it for a small stable grammar whose expression tree is useful to construct and inspect. | Avoid it for a large language needing robust parsing, diagnostics and optimization; established parser tools are more appropriate. | Grammar nodes give expressions meaning. |
| [Iterator](behavioral/iterator/README.md) | Behavioral Pattern | Use standard iterators or ranges to expose traversal without exposing storage details. | Avoid a custom iterator when returning existing const iterators or a standard range is sufficient; this custom implementation is educational. | Move through data without opening the container. |
| [Mediator](behavioral/mediator/README.md) | Behavioral Pattern | Use it when interaction rules between several peers are becoming tangled. | Avoid it for one simple callback or when components have no meaningful coordination rules. | Peers talk through a coordinator. |
| [Memento](behavioral/memento/README.md) | Behavioral Pattern | Use it for checkpoints where the originator can define a consistent state snapshot. | Avoid it when state is huge, resources cannot be restored, or recording inverse operations is cheaper. | Remember state without exposing it. |
| [Observer](behavioral/observer/README.md) | Behavioral Pattern | Use it when one change has several independently registered consumers. | Avoid it for one fixed dependency where a direct call is clearer, or when strict transactional consistency is required. | Publish a change, let subscribers react. |
| [State](behavioral/state/README.md) | Behavioral Pattern | Use it when state-dependent behavior and transitions spread across several operations. | Avoid it for a trivial toggle or a small explicit enum transition table that stays readable. | Same event, different state, different response. |
| [Strategy](behavioral/strategy/README.md) | Behavioral Pattern | Use it when algorithms vary independently and callers need to select a policy. | Avoid it for one stable algorithm or a single readable conditional that has no real extension pressure. | Same task, choose the algorithm. |
| [Template Method](behavioral/template-method/README.md) | Behavioral Pattern | Use it for a stable sequence with a few well-defined subclass extension points. | Avoid it if steps must be rearranged at runtime or composition would make dependencies clearer. | Keep the recipe, vary the steps. |
| [Visitor](behavioral/visitor/README.md) | Behavioral Pattern | Use it when element types are stable but new operations are frequent. | Avoid it when new element types are frequent or exposing their details would break encapsulation. | Stable types, new operations. |
